# Embedding 到 logits：沿当前真实批次逐步核对形状

本页承接 [模型构建](3.模型构建.md) 和 [FFN 矩阵与梯度](3.1.FFN矩阵与梯度.md)。仍然用当前的 128 维、两层教学模型，沿着同一批数据回答三个问题：

- `[1,63]` 个整数，为什么能查出 `[1,63,128]`？
- 输入都是 128 维，为什么 Q 是 128 维，K/V 却各是 32 维？
- 最后的 128 维表示，怎样得到 6400 个候选 token 的分数？

先运行配套脚本，边看实际输出边读：

```bash
.venv/bin/python scripts/inspect_model.py
```

它从真实 `model(X)` 保存中间结果，逐项重算查表、投影、因果 Attention 和词表打分，并与实际模型对照。只观察前向，不执行 backward 或更新，也不保存模型文件。

## 1. 固定本次实验，先认清每个数字

| 条件 | 本次实际值 | 含义 |
| --- | --- | --- |
| tokenizer | `model/`，词表大小 6400 | 与课程原始小模型一致 |
| 原文 | `MiniMind is a small language model project for learning how pretraining works.` | `dataset/demo_pretrain.jsonl` 第 0 条 |
| B | 1 | 这一批有一条样本 |
| T | 63 | 每条样本有 63 个输入、预测位置，包含 padding |
| H | 128 | 每个位置的隐藏表示有 128 个浮点特征 |
| Q 头数 | 8 | 从 128 维中分出 8 个查询头 |
| KV 头数 | 2 | K、V 各只有 2 个头 |
| D | `128 / 8 = 16` | 每个头的宽度 |
| FFN 中间维 | 384 | 延续上一课的 gate/up/down |
| 层数、dropout | 2、0 | 两个 Block，本实验不随机丢弃激活 |

这里不用 `out/tokenizer_lesson` 中训练出的 470 词表。换 tokenizer 会改变 ID、切分和输出候选数，不能把两套实验的数字混用。

为什么 T 是 63？Dataset 先把 token 序列补齐或截断到 64，再做移位：

```text
完整 input_ids：64 个
X = input_ids[:-1]：63 个，用作已知输入
Y = input_ids[1:]： 63 个，用作下一 token 的答案
```

因此 63 不是“这句英文正好切出 63 个有效 token”。本批只有 19 个有效目标，其他目标由 `loss_mask` 排除；模型仍计算整个 `[1,63,...]` 的张量。

本页均为 CPU、float32、seed=42，先取 batch 再创建随机模型，与 `debug_train_step.py`、`inspect_ffn.py` 的顺序一致。小数用于核对这次初始化，不是训练完成后的标准答案。

## 2. 先把三种轴放到脑中

```text
X：         [1, 63]
             │   └─ 63 个位置，每个位置存一个整数 ID
             └───── 1 条样本

embedding： [1, 63, 128]
             │   │    └─ 这个位置的 128 个隐藏特征
             │   └────── 仍是原来的 63 个位置
             └────────── 仍是同一条样本

logits：    [1, 63, 6400]
             │   │     └─ 对下一 token 的 6400 个候选打分
             │   └────── 每个输入位置各有一份打分表
             └────────── 同一条样本
```

可以把数据看成摆着 63 张卡片：最初每张卡片只有一个编号；查表后每张有 128 个数；最后每张有 6400 个候选分数。卡片的数量不变，卡片上数字的用途和数量变了。

三维 `[B,T,H]` 是张量。写矩阵乘法时，临时把前两维合成 `N=B×T=63` 行，所以 `[1,63,128]` 可以按 `63×128` 理解。每行对应一个位置，列对应特征；这不是在计算“行列式”。

## 3. Embedding：先找行，再把整行拿出来

当前实际参数表：

```text
E = model.model.embed_tokens.weight
E.shape = [6400,128]

行：6400 个 token ID，编号 0～6399
列：每个 token 的 128 个可学习浮点数
```

想成一个有 6400 个格子的资料柜：ID 是格子编号，每个格子放一张写着 128 个数的卡片。编号只用于定位，ID=47 不表示拿“47 倍”向量。

本批前五个 ID 为 `[47,261,75,47,807]`，第一个输入与目标是：

```text
X[0,0] = 47   -> 当前输入片段 "M"
Y[0,0] = 261  -> 希望接出的片段 "in"
```

查表过程：

```text
X[0,0] = 47   -> E[47,:]  -> 128 个数
X[0,1] = 261  -> E[261,:] -> 128 个数
……
X[0,62]      -> 对应 ID 的一行 -> 128 个数

63 次取行，按原位置排好：
63 × 128 -> 加上 batch 维 -> [1,63,128]
```

精确到某一项：

```text
embedding[0,0,0]   = E[47,0]
embedding[0,0,1]   = E[47,1]
……
embedding[0,0,127] = E[47,127]
```

实测 `E[47,:5]` 与 `embedding[0,0,:5]` 完全相同，约为：

```text
[0.044396, 0.080257, -0.042085, 0.049926, -0.057879]
```

这里实际有 128 项，前五项只是展示。128 个维度没有预先分别命名为“名词”“颜色”等属性；它们由训练共同学习。

### 想写成 m×n，应该怎样写？

正常代码是按 ID 查表：

```python
embedding = model.model.embed_tokens(X)
torch.equal(embedding, E[X])
```

不能写成 `(63×1 的整数 ID) @ (6400×128)`，既不符合形状，也不符合 ID 的含义。

如果一定要用矩阵乘法说明等价关系，可以把每个 ID 改成长度 6400 的 one-hot 行：只有对应 ID 的位置是 1，其他位置为 0。

```text
第 0 行：只有第 47 列是 1
第 1 行：只有第 261 列是 1

one_hot(X)：63 × 6400
E：              6400 × 128
相乘：      (63 × 6400) @ (6400 × 128) = 63 × 128
```

这只是用来解释“选出指定行”；实际 `nn.Embedding` 不需要构造这张 one-hot 矩阵。

同一个 ID 在不同位置，刚查出的向量相同，例如位置 0 和 3 的 ID 都是 47。经过位置编码和上下文处理后，各位置的隐藏表示可以不同。

## 4. 进入 Attention：先归一化，再用三套配方

第一层实际顺序为：

```text
embedding [1,63,128]
-> dropout，本配置为 0
-> input_layernorm，也就是 RMSNorm
-> a [1,63,128]
-> 分别送入 q_proj、k_proj、v_proj
```

后面用 `a` 表示这份真实 Attention 输入。RMSNorm 调整数值尺度，不改变形状。第二层则接收第一层输出的归一化表示，而不是重新查一次 Embedding。

可以把同一个位置的 128 个数看成一份资料：

- Q：根据资料形成“我要匹配什么”的查询。
- K：根据资料形成“我能与哪些查询匹配”的索引。
- V：根据资料形成“被读取时提供什么内容”的向量。

三者都由可训练权重计算；不是人工填写的文字标签。K 与 V 的形状相同，但使用不同参数，因此数值和作用不同。

## 5. Q/K/V 的每一步矩阵行列

当前第一层有四张独立的投影权重，全部 `bias=False`：

| 权重 | PyTorch 保存形状 | 计算时使用的转置 | 参数数 |
| --- | --- | --- | --- |
| Wq / `q_proj.weight` | `128×128` | `128×128` | 16,384 |
| Wk / `k_proj.weight` | `32×128` | `128×32` | 4,096 |
| Wv / `v_proj.weight` | `32×128` | `128×32` | 4,096 |
| Wo / `o_proj.weight` | `128×128` | `128×128` | 16,384 |
| 本层投影合计 | 四张矩阵 | 不包含 Norm 和 FFN | 40,960 |

Linear 保存的是 `[输出特征数,输入特征数]`，所以数据排成行时，计算为 `输入 @ weight.T`。即使 Wq 是方阵，转置也会交换数值的位置，不能因为形状不变就省掉。

```text
a：      63 × 128

Q = a @ Wq.T：
    (63 × 128) @ (128 × 128) = 63 × 128 -> [1,63,128]

K = a @ Wk.T：
    (63 × 128) @ (128 × 32)  = 63 × 32  -> [1,63,32]

V = a @ Wv.T：
    (63 × 128) @ (128 × 32)  = 63 × 32  -> [1,63,32]
```

三条支路使用同一个 a，各自读取全部 128 项，不是把输入分成三段。所有 63 个位置使用相同的 Wq/Wk/Wv。

### 缩到第一个位置，K 的一个数怎样算

```text
a[0,0,:]：1 × 128
Wk.T：      128 × 32

K[0,0,:] = (1 × 128) @ (128 × 32) = 1 × 32
```

第 0 个输出通道为：

```text
K[0,0,0]
= a[0,0,0]   × Wk[0,0]
+ a[0,0,1]   × Wk[0,1]
+ ...
+ a[0,0,127] × Wk[0,127]
≈ -0.229307
```

第 1 个通道改用 Wk 第 1 行，直到第 31 行。V 的计算结构一样，换用 Wv；本次 `V[0,0,0]≈-0.906810`。

因此“128→32”是 32 套不同的加权求和，每套都读取 128 项；不是只保留输入前 32 项，也不是简单每四项取平均。

### 为什么恰好是 32？

```text
每头宽度 D = hidden_size / Q头数 = 128 / 8 = 16
Q 的输出宽度 = 8 个头 × 16 = 128
K 的输出宽度 = 2 个头 × 16 = 32
V 的输出宽度 = 2 个头 × 16 = 32
```

本例使用 GQA，即 Grouped Query Attention，分组查询注意力。减少的是 KV 的头数，单头仍然是 16 维，才能与 Q 的单头做匹配。

32 由结构配置决定，不是训练后“发现只需要 32 维”。这些投影权重由初始化或 checkpoint 提供，训练改变它们的数值，不改变这里的行列数。第二层有自己独立的四张投影矩阵。

## 6. 分头与 RoPE：形状变了，发生了什么？

投影后，每个位置先有一长排数；分头只是把这一排分段摆放：

```text
Q：128 项 -> 8 组，每组 16 项
[1,63,128] -> view -> [1,63,8,16]

K：32 项 -> 2 组，每组 16 项
[1,63,32]  -> view -> [1,63,2,16]

V：32 项 -> 2 组，每组 16 项
[1,63,32]  -> view -> [1,63,2,16]
```

例如第一个位置的 K 头 0 取 `K[0,0,0:16]`，头 1 取 `K[0,0,16:32]`。这里 `view` 不训练参数，也不重新加权求和，32 个数仍是那 32 个数。

接着 RoPE 根据位置旋转 Q/K 的成对分量：

| 对象 | RoPE 前 | RoPE 后 | 是否改变内容 |
| --- | --- | --- | --- |
| Q | `[1,63,8,16]` | `[1,63,8,16]` | 依位置旋转，形状不变 |
| K | `[1,63,2,16]` | `[1,63,2,16]` | 依位置旋转，形状不变 |
| V | `[1,63,2,16]` | `[1,63,2,16]` | 本实现不对 V 做 RoPE |

位置 0 的旋转角度是 0，后续位置按不同频率旋转；不要因为前后形状相同就认为 RoPE 没有参与计算。具体配对方式见 [模型构建的 RoPE 一节](3.模型构建.md)。

## 7. 两个 KV 头，怎样供八个 Q 头使用？

`repeat_kv(...,4)` 将每个 KV 头重复四次，匹配 Q 的 8 个头：

```text
原 K/V 头：        [0, 1]
按头重复后的排列：[0,0,0,0, 1,1,1,1]

Q 头：             0 1 2 3  4 5 6 7
使用的 KV 头：     0 0 0 0  1 1 1 1
```

形状变化为：

```text
K/V：[1,63,2,16] -> repeat_kv -> [1,63,8,16]
Q：  [1,63,8,16]              -> 不需要重复

再把“位置轴”和“头轴”交换：
Q/K/V 都变成 [1,8,63,16]
```

重复没有产生新的可训练权重，也没有把单头宽度变成 64。四个 Q 头使用相同的 K/V 内容，但 Q 向量可以不同，所以通常能形成不同的匹配权重和汇总结果。

`transpose(1,2)` 交换轴后，每个头的 `63×16` 小矩阵便于单独做 Attention；它与 Linear 的权重 `.T` 都是在交换轴，但操作的对象、维度不同。

若启用 KV Cache，本实现保存重复之前的 `[B,历史长度,2,16]`，每层单独一份。本页不启用缓存，query 与 key 长度都为 63。

## 8. Attention 内部：先得到 63×63，再汇总成 63×16

只看 batch 0、头 0，仍然使用实际的 63 个位置与 16 维：

```text
q：63 × 16       每行是一个位置的查询
k：63 × 16       每行是一个位置的索引
v：63 × 16       每行是一个位置提供的内容

匹配分数：
scores = (q @ k.T) / sqrt(16)
       = (63 × 16) @ (16 × 63) / 4
       -> 63 × 63
```

这张分数表的行是“谁在查询”，列是“查询谁”：

```text
scores[i,j] = 第 i 个位置的 Q 与第 j 个位置的 K 的匹配分数
```

对未来位置 `j>i` 设为负无穷，再沿每行的 key 位置做 softmax。未来项的权重为 0，可见项的权重加起来为 1。

实际第 0 个 query 只能看位置 0，因此其注意力权重是：

```text
[1,0,0,...,0]，共 63 项
```

它随后读取当前头的 V：

```text
weights：   63 × 63
v：              63 × 16
attended = (63 × 63) @ (63 × 16) = 63 × 16
```

以位置 i 的输出第 d 项为例：

```text
attended[i,d] = Σ weights[i,j] × v[j,d]
               j 取允许读取的位置 0～i
```

所以 Attention 是“按匹配权重汇总各位置的内容”。这里 softmax 的 63 个候选是输入位置，不是词表中的 6400 个 token。

把全部 8 个头放回去：

```text
Q @ K转置： [1,8,63,16] @ [1,8,16,63] -> [1,8,63,63]
softmax：   [1,8,63,63]，沿最后一维归一化
weights @ V：[1,8,63,63] @ [1,8,63,16] -> [1,8,63,16]
```

脚本把这几步显式重算，并与真实 Attention 的合头结果比较。模型使用 SDPA 时可以融合计算，无需真的在 Python 里保留整张注意力表；显式展开是为便于学习。float32 不同求和顺序允许有很小误差。

## 9. 为什么还能回到 128 维？

每个 Q 头分别得到一个 16 维汇总结果，8 个头拼回一排：

```text
[1,8,63,16]
-> transpose，先把每个位置的头排到一起
[1,63,8,16]
-> contiguous + view，合并最后两维
[1,63,128]           因为 8 × 16 = 128
```

这里是拼接各头结果，不是对 8 个头取平均，也不是把原始 32 维 K/V 直接送入一个“32→128”的 Linear。

之后才做 Attention 的输出投影：

```text
merged：   63 × 128
Wo.T：          128 × 128
o_proj：  (63 × 128) @ (128 × 128) = 63 × 128
还原 batch 维：[1,63,128]
```

Wo 学习怎样混合这些头提供的特征。然后 Attention 输出与该段原输入逐元素相加，经过下一次 RMSNorm、FFN 和 FFN 残差：

```text
Block 输入 r                         [1,63,128]
a = RMSNorm(r)                       [1,63,128]
attention_out = Attention(a)         [1,63,128]
s = r + attention_out                [1,63,128]
ffn_out = FFN(RMSNorm(s))            [1,63,128]
Block 输出 = s + ffn_out             [1,63,128]
```

FFN 内部的 `128→384→128` 逐步计算见 [上一课](3.1.FFN矩阵与梯度.md)。第二个 Block 再做同类处理，最后再做一次 RMSNorm，才得到 lm_head 的输入 h。

保持 `[1,63,128]` 只表示位置数和宽度没变；每一阶段里面的数值已经经过了不同运算。

## 10. lm_head：同一份 128 维资料，给 6400 个候选逐个打分

此时：

```text
h：[1,63,128]，第二个 Block 后再经最终 RMSNorm 的上下文表示
lm_head.weight：[6400,128]
```

把 lm_head 的 6400 行想成 6400 份评分配方。第 j 行专门计算候选 ID j 的分数，每份配方都读取 h 的全部 128 项。

```text
全部 63 个位置：
(63 × 128) @ (128 × 6400) = 63 × 6400
还原 batch 维 -> logits [1,63,6400]

只看第 0 个位置：
(1 × 128) @ (128 × 6400) = 1 × 6400
```

本模型将输入 Embedding 与 lm_head 绑定为同一个参数对象：

```python
E is model.lm_head.weight
```

预期为 `True`。所以最终计算可以写为：

```python
logits = h @ E.T
```

同一张 `6400×128` 表，输入和输出时用法不同：

| 时刻 | 已知什么 | 对 E 做什么 | 得到什么 |
| --- | --- | --- | --- |
| 输入 Embedding | 每个位置的 ID | 按 ID 查对应行 | 该 ID 的 128 维向量 |
| 输出 lm_head | 每个位置处理后的 h | 与全部 6400 行分别做点积 | 对 6400 个候选的分数 |

共享参数数为 `6400×128=819,200`，只计一次。它不是两张数值碰巧相同的表；优化器更新的是同一个参数，反向会汇总输入查表与输出打分等相关路径的贡献。

这也不是“把 Embedding 反过来，恢复原来的 ID”。h 已经过两个 Block，目标是预测下一个 token，而不是识别最初输入的是谁。

### 把第一个位置的正确候选分数写开

第一个位置的目标是 `"in"`，ID=261：

```text
logits[0,0,261]
= h[0,0,0]   × E[261,0]
+ h[0,0,1]   × E[261,1]
+ ...
+ h[0,0,127] × E[261,127]
≈ 0.382358
```

其他 6399 个候选也各算一次这样的 128 项点积。模型不是先知道 Y=261，再只算这一项；训练用完整的候选分数表评价正确项。

本次实测：

| 第 0 个预测位置 | 结果约为 | 怎样理解 |
| --- | --- | --- |
| 目标 token | ID 261，`"in"` | 来自 Y，不由模型猜测产生 |
| 目标 logit | 0.382358 | 未归一化分数，可以为正也可以为负 |
| 目标概率 | 0.00019090 | 对该位置全部 6400 个分数做 softmax 后取得 |
| 当前最大分数 | ID 6207，`" fraud"`，2.034601 | 随机模型的当前猜测，不是正确答案 |
| 此位置 loss | 8.563768 | `-log(目标概率)` |
| 本批 masked loss | 8.943250 | 汇总 19 个有效目标，不只看第 0 个位置 |

单个 logit 不能独自决定概率；还要与同一位置其余 6399 个分数共同归一化。调用 `F.cross_entropy` 时直接传原始 logits，它内部完成相应计算。

## 11. 两处 softmax，别把候选对象搞混

| 位置 | 输入形状 | 最后一维是什么 | 回答的问题 |
| --- | --- | --- | --- |
| Attention | `[1,8,63,63]` | 63 个 key 位置 | 当前查询要从哪些位置汇总内容？ |
| 词表概率 | `[1,63,6400]` | 6400 个 token 候选 | 下一个 token 更可能是哪一个？ |

模型 forward 返回的是 logits，没有在 lm_head 后自动返回词表概率。脚本里的词表 softmax 用来展示概率与 loss 的对应关系。

训练默认 `logits_to_keep=0`，本实现的 `slice(-0,None)` 等价于保留全部位置，得到 `[1,63,6400]`。每个有效位置都在学预测自己的下一个 token。

生成时通常只需要当前末尾位置的一份分数，设置 `logits_to_keep=1` 后得到 `[1,1,6400]`。这只减少输出打分的位置数，候选数仍然是 6400。

另外：

```text
logits.argmax(dim=-1)：[1,63]
```

它给每个位置选一个最高分 ID，并不是把 63 个预测依次接回去进行 63 次生成；后者每一步还要用此前已生成的内容。

## 14. 再做两个真实数值实验，区分形状与语义

### 相同 ID，为何最后的表示可以不同

位置 0 和 3 的输入都是 ID 47，所以刚查表时完全相同；位置不同、可读前文不同，经过 Block 后的 h 则可以不同。Embedding 行相同不意味着整个网络可以跳过重复 token 的计算。

### 每项 logits 都加 10，概率会怎样

对同一个位置的全部候选一起加常数 c：

```text
softmax(z+c)[j]
= exp(z[j]+c) / Σ exp(z[k]+c)
= exp(c)*exp(z[j]) / (exp(c)*Σ exp(z[k]))
= softmax(z)[j]
```

这说明 logits 没有单独的绝对概率单位，候选间的相对差才影响 softmax。只给正确候选加 10 则是另一件事，会改变其相对分数。

```python
# doc-example: contextual-hidden-and-logits
import torch
from torch.utils.data import DataLoader, Subset
from dataset.lm_dataset import PretrainDataset
from scripts.lesson_lab import tokenizer, small_model
from trainer.train_utils import setup_seed

torch.set_num_threads(2)
setup_seed(42)
ds = PretrainDataset("dataset/demo_pretrain.jsonl", tokenizer(), max_length=64)
X, Y, mask = next(iter(DataLoader(Subset(ds, [0]), batch_size=1)))
model = small_model()
with torch.no_grad():
    result = model(X)
    embeddings = model.model.embed_tokens(X)
    scores = result.logits
assert X[0, 0] == X[0, 3] == 47
assert torch.equal(embeddings[0, 0], embeddings[0, 3])
assert not torch.allclose(result.last_hidden_state[0, 0], result.last_hidden_state[0, 3])
torch.testing.assert_close(scores.softmax(-1), (scores + 10).softmax(-1))
assert torch.equal(scores.argmax(-1), (scores + 10).argmax(-1))
print("相同输入 ID 产生不同上下文表示；全体候选平移不改变概率")
```

本段沿真实文本创建同结构的 128 维模型；`small_model()` 的位置表长度为 128，前 63 个位置的频率规则与本课 64 长度配置相同。没有修改原模型权重文件。
